1. EXECUTIVE SUMMARY
================================================================================

The Happy Balance application has search functionality implemented in both the
frontend and backend. The search is currently:

  ✓ Case-insensitive (works correctly)
  ✗ NOT Accent-insensitive (does NOT work with accented characters)

Examples of current limitations:
  - Searching "cafe" will NOT find transactions with merchant "Café"
  - Searching "senor" will NOT find category named "Señor"
  - Searching "panama" will NOT find merchant "Panamá"

6. CODE SNIPPETS - CURRENT IMPLEMENTATION
================================================================================

FRONTEND - FilterService.ts (matchesSearch function):
────────────────────────────────────────────────────
const matchesSearch = (transaction: Transaction, query: string): boolean => {
  const lowerQuery = query.toLowerCase();                    // Only lowercases
  const numericQuery = parseFloat(query);
  const isNumeric = !isNaN(numericQuery) && isFinite(numericQuery);

  const textMatch =
    transaction.merchant.toLowerCase().includes(lowerQuery) ||
    transaction.description.toLowerCase().includes(lowerQuery);

  if (isNumeric) {
    const transactionAmount = Math.abs(transaction.amount);
    const amountMatch =
      Math.abs(transactionAmount - numericQuery) < 0.01 ||
      transactionAmount.toString().includes(numericQuery.toString());
    return textMatch || amountMatch;
  }

  return textMatch;
};

BACKEND - PrismaTransactionRepository.ts (buildWhereClause):
───────────────────────────────────────────────────────────
if (filters.merchantName && filters.merchantName.trim()) {
  const searchTerm = filters.merchantName.trim();

  if (searchTerm.length <= 3) {
    where.OR = [
      { merchant: { startsWith: searchTerm, mode: "insensitive" } },
      { description: { startsWith: searchTerm, mode: "insensitive" } }
    ];
  } else {
    where.OR = [
      { merchant: { contains: searchTerm, mode: "insensitive" } },
      { description: { contains: searchTerm, mode: "insensitive" } }
    ];
  }
}

7. SOLUTION - MAKE SEARCH ACCENT-INSENSITIVE
================================================================================

EASIEST APPROACH (Frontend Only):

Create: apps/frontend/src/lib/utils/stringNormalization.ts

export const normalizeForSearch = (str: string): string => {
  return str
    .toLowerCase()
    .normalize('NFD')                  // Decompose é → e, ñ → n, etc.
    .replace(/[\u0300-\u036f]/g, '')  // Remove diacritical marks
    .trim();
};

Then use in FilterService.ts:
  const normalizedQuery = normalizeForSearch(query);
  const textMatch =
    normalizeForSearch(transaction.merchant).includes(normalizedQuery) ||
    normalizeForSearch(transaction.description).includes(normalizedQuery);

And in CategorySelectionModal.svelte:
  normalizeForSearch(cat.name).includes(normalizeForSearch(searchTerm))

BENEFITS:
- Simple to implement
- No database changes needed
- Works immediately
- Good performance for typical transaction lists

9. KEY TECHNICAL DETAILS
================================================================================

UNICODE NORMALIZATION:
- Method: String.prototype.normalize('NFD')
- Removes: Diacritical marks (accents)
- Browser Support: Chrome 34+, Firefox 29+, Safari 11+, All modern browsers

PRISMA CASE-INSENSITIVITY:
- Parameter: mode: "insensitive"
- Database: PostgreSQL
- Limitation: Only handles case, NOT accents
- Alternative: Use PostgreSQL unaccent extension (requires setup)

PERFORMANCE CHARACTERISTICS:
- Small lists (< 1,000): No noticeable impact
- Medium lists (< 10,000): Minimal impact, < 1ms per search
- Large lists (> 100,000): May need debouncing or server-side filtering
